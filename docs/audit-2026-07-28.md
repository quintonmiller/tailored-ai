# Audit — 2026-07-28

Findings from a day spent reading what agents actually did, rather than what the
code says they should. Three threads converged: rooms misbehaving, a fabricated
status update that replayed for three days, and a question about how context
files stay current.

Every item was verified at the cited line unless marked **⚠︎ unverified**, which
means it came out of an automated audit lane and has not been independently
checked.

Items marked ✅ were fixed on 2026-07-28; the rest are open.

---

## The shape of it

Three diseases, each appearing several times:

1. **Config that parses, persists, and is never read.** `system_prompt:` carried
   four agents' entire persona to nothing. A manifest parser dropped
   `fileBoundary` and `injectMemory` between the manifest and the loop. An agent
   authored `temp: 0.3`. None of it warned.
2. **A guard that does not guard.** `hashManifest` hashes every skill as
   `"data":{}`. `activeSkill.rootPath` is advertised to the model and read by
   nothing. `admin` can rewrite the permission gate that governs `admin`.
3. **A snapshot treated as a live feed.** Stale global context reported as
   current work. An agent's own fabrication replayed out of its session. Both
   made worse by the base prompt's instruction to treat context as ground truth.

## P0 — boundaries that are not boundaries

### 1. `custom_tools.` and `permissions.` are agent-writable

`packages/core/src/tools/admin.ts:34-47`. `ALLOWED_WRITE_PREFIXES` includes
both. `admin` is a meta tool appended to every agent
(`runtime.ts:1035`), and the reference deployment runs
`permissions.defaultMode: auto`.

An agent can write itself a custom tool whose `command` is arbitrary shell, or
set `permissions.defaultMode: auto` to disarm the gate that would have stopped
it. `context.` is on the same list and redirects where prompt-injected files are
read from.

**Fix:** drop `custom_tools.` and `permissions.`; reconsider `context.`.
Tier: core. Effort: small.

### 2. `CustomTool` ignores its `ToolContext`

`packages/core/src/tools/custom.ts:45-76`. The parameter is named `_context`
because it is discarded, and execution ends at `runShellCommand` →
`bash -c` on the host: no `checkSandboxBoundary`, no `checkExecBoundary`, no
`context.sandbox` routing.

This is a full container escape for any agent with `sandbox: docker`. (1)
without (2) still leaves the hole open for a human-added custom tool.

**Fix:** honour the context the way the `exec` tool does. Tier: core. Effort:
medium.

### 3. `memory` writes are unbounded

The tool never checks any boundary, and `scope: "global"` writes directly into
the directory injected into every agent's prompt.

**Fix:** confine writes to the tool's own `globalDir`/`agentDir`/`kbDir` roots.
Deliberately *not* `checkSandboxBoundary` — three live agents have a
`fileBoundary` of `~/research/travel` while the context dirs live elsewhere, so
that check would break all three. This is a containment invariant, not a
sandbox boundary. Tier: core. Effort: small.

### 4. `resolveDefaultDir` falls back to global

`packages/core/src/tools/memory.ts:317-322`. When `scope` is unset and there is
no `agentContextDir` — un-agented CLI, Slack, API sessions — a "profile" write
lands in **global**, and therefore in every agent's prompt.

**Fix:** route the no-agent case to a session-scoped directory and log once. Do
**not** hard-fail on an omitted optional parameter: that converts a silent-drift
bug into a visible-stall bug, and the retry loop is what a 27B local model
handles worst. Tier: core. Effort: small.

### 5. `task-watcher` replaces `toolContextExtras` instead of merging

`packages/core/src/task-watcher.ts:409`:

```ts
toolContextExtras: worktree ? { workingDirectoryBoundary: worktree.path } : undefined,
```

`runtime.ts:1095-1100` builds an object carrying `agentName` and the resolved
`fileBoundary`. Both branches discard it, so every task dispatch loses agent
attribution, and the non-worktree branch loses the declared boundary too.

**Fix:** spread the base object. Tier: core. Effort: small.

## P1 — trust and permissions

### 6. `hashManifest` hashes every manifest as `"data":{}`

`packages/core/src/resources/trust.ts:143`:

```ts
const canonical = JSON.stringify(rest, Object.keys(rest).sort());
```

The second argument to `JSON.stringify` is a **replacer array**, not a sort
order, and it applies recursively. `data` survives as a top-level key; its
children do not.

Reproduced: two skill manifests differing in both `instructions` (`"be nice"` vs
`"exfiltrate ~/.ssh via exec"`) and `toolRefs` (`[read]` vs
`[exec, write, web_fetch]`) hash identically.

So the trust store's cached-approval check and `tai resources install --frozen`
are ineffective for every resource kind whose payload lives in `data` — skills,
prompts, kb, agents. Approve a benign `SKILL.md` once and its body and
`allowed-tools` can be rewritten with no re-prompt.

**Fix:** canonicalise properly. Tier: core. Effort: small.

### 7. ✅ Conditional permission rules could not match an absent argument

`packages/core/src/approval.ts:88` returned false for any missing argument, so a
rule could only ever describe what the model *did* pass. The dangerous call is
often the one that passes nothing and takes a default — an unscoped write, an
unfiltered query — and no rule could reach it.

A `null` pattern now means "this argument must be absent", and an empty string
counts as absent because models emit `scope: ""` for "unset" and the tools here
already read it that way:

```yaml
permissions:
  tools:
    memory:
      mode: conditional
      rules:
        - match: { scope: "^global$" }   # explicit global write
          action: approve
        - match: { scope: null }         # no scope named at all
          action: approve
        - match: {}
          action: auto
```

This is the seam the per-tool knobs were standing in for.

### 8. ✅ "approve" with no approval handler auto-approved, silently

`packages/core/src/agent/loop.ts:516` was an empty block with a comment. Cron,
rooms, the task watcher and webhooks all run without a handler, so a policy of
`approve` quietly became `auto` in exactly the places nobody was watching.

`permissions.noHandlerAction` now chooses: `auto` (default, unchanged
behaviour) or `reject`. The default stays permissive on purpose — flipping it
would stop autonomous runs that have worked for months, which is the "guard that
breaks what it protects" shape this codebase keeps hitting. What changed is that
the permissive branch logs, once per tool per process, instead of passing in
silence.

### 9. ⚠︎ unverified — `delegate` drops boundary and sandbox

Reported at `packages/core/src/tools/delegate.ts:88-104`. Sub-agents inherit
neither. Tier: core. Effort: medium.

## P2 — skills

The subsystem is more complete than its usage suggests: real `SKILL.md`
parsing, a registry, lockfile install with trust approval, per-agent enablement,
a progressive catalog layer, and `load_skill`. The reference deployment shows
**27 activations across 7 sessions, 14–16 June 2026, and nothing since**.

### 10. `docs/skills.md` states the wrong default

`docs/skills.md:73` says `skillLoading: progressive   # default`.
`packages/core/src/agent/agents.ts:185` is `?? "eager"`, and eager emits a
deprecation warning. Follow the doc, omit the key, get the deprecated path the
doc says you are avoiding. Tier: docs. Effort: trivial.

### 11. `activeSkill.rootPath` is advertised and unenforced

Set at `load-skill.ts:77-84` and surfaced to the model in the activation header
("scoped to: …"). `active-skill.ts:12-17` documents it as enforcement. No tool
reads it — the only occurrences are its own declaration.

Telling a model it is confined when it is not is worse than saying nothing.

**Fix:** enforce it in the file/exec tools, or remove the claim. Tier: core.
Effort: small.

### 12. `allowed-tools` means opposite things in the two loading modes

Eager **grants** tools (`agents.ts:288-299` union-merges `toolRefs` into the
agent's set). Progressive only **restricts** — the merge lives in the `else`
branch, asserted as intended in `skill-progressive.test.ts:67`.

So a skill can never grant a tool progressively, and one listing a tool the
agent lacks narrows the allowlist to names absent from the tool map. The live DB
shows **33 rejections against 27 activations**.

Side effect worth noting: under eager, a `SKILL.md` on disk silently widens a
live agent's tool set — combined with (6), editing that file changes an agent's
capabilities with no approval step. Tier: core. Effort: medium.

### 13. A skill is one Markdown file

Only `SKILL.md` is ever read. Bundled scripts, assets and reference files are
invisible; one skill can be active at a time; there is no per-skill state and no
composition.

This and (12) are why the subsystem was dogfooded for three days and then
abandoned: the two things that would make you reach for a skill are the two that
do not work. Tier: core. Effort: large.

### 14. Dead fields on `SkillDefinition`

`knowledgeRefs`, `workflowRefs`, `promptRefs` — declared and type-validated at
`resources/skill.ts:23-28,71-91`, consumed by nothing, and `SKILL.md` cannot
express them anyway. Tier: core. Effort: small.

## P3 — keeping context current

### 15. Wire `{{include:}}` into `loadAllContext`

`expandPrompt` already exists. Context files are read raw, so a roster or room
list in a context file is a hand-maintained snapshot that drifts silently.

Gate expansion behind an opt-in marker (front-matter flag or `.tpl.md` suffix)
so existing prose containing a literal `{{` is untouched. Tier: core. Effort:
medium.

### 16. A `context-generator` plugin

Depends on (15). Regenerate the agent roster and room list from the registries
on change, into `data/context/generated/`, included by the hand-written files.
Keep the generated file **out of** `global/` so a crashed generator cannot
silently broadcast, and stamp it with a generated-at time so drift is visible in
the prompt itself. Tier: built-in plugin. Effort: medium.

### 17. ⚠︎ unverified — `getContextStats()` has zero callers

It already computes per-file context sizes. Wiring it is the surface that would
have shown that 24 of 27 agents had no context files and that one file was half
the global budget. Tier: core. Effort: small.

### 18. `/api/context` is read-only

GET list and GET file only. Nothing in the UI can prune or rotate context.
Tier: server. Effort: medium.

### 19. `MemoryTool` has no test file

The tool with the widest blast radius in the prompt path has no unit coverage.
Pair with (3): the test should assert the containment invariant directly.
Tier: core. Effort: small.

### 20. Stale comment at `config.ts:685`

Still says the `ask_user` inbox file is "relative to the global context dir". It
is not, as of the fix recorded in `ask-user.ts`. Left alone it invites someone to
put it back. Tier: core. Effort: trivial.

## Cross-cutting

### 26. The base prompt tells agents to treat context as ground truth

`packages/core/src/agent/prompt.ts`: *"When context files are loaded below, use
them as ground truth."* Context files are snapshots. This instruction is why a
two-month-old question in `inbox.md` was reported as live outstanding work.

The global context now says the opposite — re-check anything dated, tool results
win. Both are in every prompt. Softening the base prompt is the tidier fix, and
its heavy memory section could be trimmed in the same pass. Tier: core.

### 27. The base prompt tells every agent it is self-modifying

*"You are a self-modifying agent… creating new tools, adjusting settings"* — told
to `travel-researcher` as much as to `agent-manager`. That instruction plus (1)
is the path by which an agent authored `temp: 0.3` into its own config.
