A commitment's `nextCheck` is now read as a time or a change to watch for. With the directory on (`builtin:directory`), the `commitment` tool reads it as it's written and says what it made of it, the way `schedule` echoes a booking: "Friday 9am", "in 2 days" or "2026-10-28" become a moment in the runtime's time zone ("Check: Fri, Oct 23, 09:00, in 22h."), and "when plan/lisbon changes", "when plan changes" or "when a booking changes where status=confirmed" become a change to watch for, with a backstop a week out. Anything else stays a note: the update still goes through, and the reply says nothing will wake the agent for it and lists the forms that would. A change can only be one the agent it wakes can read. What the directory reads is kept beside the text in new commitment fields, `checkAt` (UTC), `checkOn` (`{ type, id?, where? }`), `checkedAt` and `checkEvents`, and they follow the text: a person's edit of `nextCheck` on the State page, the agent's page or a room's page is read again the same way, even when another write lands in between. On a room's commitment, a person's `nextCheck` holds like their other edits; the fields beside it never do. A commitment's line (in the tool's replies, its listings and the "Your commitments" block) says the check as the directory read it, so "in 2 days" reads as the day it meant rather than going stale. When the directory starts, an open or waiting commitment written before this whose `nextCheck` is a date or a change is read once, so it wakes its owner like a new one (one whose date has passed is due at once); a relative one ("in 2 days", "Friday") is left as written until it's next written.

The agent page's Working on list shows each check as the time it was read as and how far off it is (the words as written on hover), or "(a note)" for text nothing wakes the agent for, and when it was last checked, and pressing the check changes it. A room's page shows the same, and its Edit form takes the next check; `PATCH rooms/:room/commitments/:id` accepts `nextCheck`.

`schedule`'s `when` (and so a check's time) also takes a weekday: "friday", "friday 9am", "mon at 14:00", "next friday", meaning the next one whose time is still ahead, 09:00 when no time is given.

Commitments now wake their owner when their check comes due. Every thirty seconds the directory looks for open and waiting commitments whose `checkAt` has come and wakes each one's owner (a room's lead, for a room's own), one at a time per runtime, through `runtime.wakeAgent`, in the session `commitment:<id>` with `wake.kind: "commitment"`, so the pause, an online agent's own switch and its hourly wake ceiling apply, and each check counts as one of its `rooms.maxWakesPerHour`. A check is claimed before its turn by moving it an hour on and setting `checkedAt`, so a slow turn never runs twice, across a reload too, and a turn that never ends (TAI stopped mid-turn) comes round again an hour later instead of never. Paused for everyone, a look reads nothing and every check stays due; an agent switched off or paused on its own is passed over, so its checks don't hold up anyone else's. At the ceiling a check comes round five minutes on, or when the hour has room if that's later. A change a commitment watches for makes it due at once with the change's line kept, and a burst of changes becomes one wake that lists them; a change counts only when the agent can read what changed and it wasn't its own, and a week with none wakes it anyway. The line says what changed, values included, only when the changed record is global or in the commitment's own scope and of a type anyone may read; otherwise it names no more than the commitment already does ("plan/lisbon changed; read it to see how"), since everyone who reads the commitment reads the line. The turn is told the commitment, how to tell it's done, its next step, its three newest updates, why it's due and what it may do, in about 120 tokens, and asked to do the next step and update the commitment with a new check. A turn that writes no update gets "Checked; no change." written for it, marked `kind: "check"`, which doesn't count as the work moving ("last update", the page and upkeep's "no update in a while" skip entries with that mark); with no new check, a check on a time comes round 1, 2, 4, then every 7 days, and a check on a change goes back to waiting with its week's backstop. A check the agent set to a note during its turn stays a note. Finished, dropped and archived commitments never wake, nor does an agent with no `commitment` tool. Upkeep no longer reports a check the directory read as come, since the check itself wakes the agent. `checks: false` in the plugin's config wakes no one for a check; `nextCheck` is still read, and upkeep then reports a time check that has come.

Behaviour you will notice: until autonomy is enforced, every check's turn asks first, whatever the commitment's `autonomy` says, so `tell` and `quiet` behave like `suggest`. A call in such a turn that writes or can't be undone is refused through `agent.pre_tool_use` with "This commitment asks first: put it in nextStep and set the commitment waiting on a person."; a call to a tool that declares no effect is refused with `"<tool>" isn't open to a commitment check yet: note in nextStep what you'd use it for.` The agent's own `commitment`, `writeup` and `directory` go through, and so do calls that declare they only read. Core's `state` tool now declares its effect per call (`read` for `types`, `get`, `query` and `search`, `write` for the rest) and `read` declares `read`, so a check can read what it watches. The loop's own checks treated both as reads already, so nothing in the loop changes; a hook on `agent.pre_tool_use` that matches `effectDeclared: false` no longer sees these two tools, and one that matches `effect: write` now sees `state`'s writes. Most other tools declare no effect yet, so most are refused in a check's turn. A person's chat and every other turn are unaffected.
